# 修罗领取被拒（人数不足）→ 补人 → 重领 全链路时序

从「领取过程中发现队伍人数不够」到「补齐后重新领取成功」的完整行为与时间间隔。
间隔均为代码内实测校准常量（xiuluo.py / team.py / wubei.py / workflows/team_flow.py），
改动前先读本表。

> 2026-11-13：监控/建队/喊话/非队长保持已下沉 `workflows/team_flow.py`，
> 任务侧 `_monitor_team_and_fill` 等为薄包装；最少人数、喊话内容、自动归队
> 开关按任务由 `TeamFlow` 配置注入，行为与间隔不变。

五倍（wubei.py）为同款镜像逻辑，唯一差异：`target` 固定 5、无最少人数设置、
无必须种族设置（喊话内容在五倍设置里单独配置，默认「百次五倍来人，效率队」；
修罗喊话内容同样可配置，默认「百次修罗来人，效率队，来{种族}」，`{种族}`
替换为必须种族/无要求时为「随意来人」）。下文中「修罗」的说法同样适用于五倍。

## 1. 领取时发现人数不够的两个触发点（_claim_task 内）

| 触发点 | 出现条件 | 检测节奏 | 行为（min_members=5） |
|---|---|---|---|
| 领取确认弹窗（TEAM_CONFIRM_TEXT） | 队伍 3~4 人，游戏询问是否仍要领取 | 点完选项后弹窗约 0.5~1s 出现；对话框轮询每 0.3s 截帧+OCR；OCR 漏检时第 2 轮一次性 2x 放大补识 | 点「我再想想」拒绝 → 进监控补人循环 |
| 「战斗力异常强大」警告（TEAM_WARNING_TEXT） | 队伍 <3 人 | 同一轮询内同帧检出 | 点屏幕中间一次关闭对话框 → 进监控补人循环 |

min_members 设 3/4 时确认弹窗点「确定」接受领取，任务照常领走，不进补人流程；
但领取后队伍掉到 3 人以下时警告路径仍会触发。

## 2. 监控循环逐轮行为（_monitor_team_and_fill，人满才返回 / 非队长不返回）

每轮固定顺序，间隔如下：

| 步骤 | 行为 | 耗时/间隔 |
|---|---|---|
| 1. 截帧查申请人证据（申请面板已开 或 zudui_item2 命中） | 命中 → 走补人子流程（第 3 节） | ~0.1-0.3s |
| 2. 无证据 → _check_team_with_retry（一次面板开合查队长+人数） | 见第 4 节 | 实测 5~7s/次 |
| 2a. 瞬态失败重试 | 「队长无法判定」/「截图失败」→ sleep 2s 再查，最多 3 次 | 2.0s × 2 |
| 3. 结果分派 | 见下表 | — |

结果分派：

| 结果 | 后续行为 | 间隔 |
|---|---|---|
| ready（人满） | 监控循环返回，走第 5 节 | — |
| wait（缺人无申请人） | 复查申请人证据 → 无则喊话+等待 | sleep 10s 重查（识别失败类 3s） |
| wait + 复查到申请人（2026-11-02 新增） | 立即补人，不 sleep | 0 |
| not_leader 确定性（未组队/面板无解散按钮） | _keep_alive 保持模式：无限循环、仅战斗线程运行，人工停止 | 永久 |
| not_leader 瞬态（遮挡/按钮未命中等） | 不退出监控，按间隔持续重查 | sleep 10s（识别失败 3s） |

缺人自动喊话：距上次 ≥30s（SHOUT_MIN_INTERVAL）才喊，一次约 1.8s
（激活 0.5s + 剪贴板粘贴 0.8s + Enter 0.5s）。

## 3. 补人子流程时序（team.fill_team，一次补满缺口）

```
max_allow = 最近一次人数检查的缺口（缺 N 补 N；申请态下查不到
            人数用最近值，未知按 1 人保守补）——2026-11-07 用户结论
点组队按钮（zudui_item2 命中即记录确定性队长）          ~0.1s
等申请加入面板出现：每 0.5s 截帧+模板，最长 3s          ≤3s（6 次）
循环（最多允许 max_allow 人）：
  选第一个未失败申请人行：区域 OCR ~0.1-0.17s + 点击 + 等选中态  0.3s
  点「允许」按钮                                        ~0.1s
  等失败提示「对方已经加入其他队伍」窗口：每 0.5s 截帧+OCR  ≤2.5s
    ├─ 失败 → 该申请人记失败换下一个，先 sleep           0.5s
    └─ 成功校验：截帧 OCR 确认该行从列表消失              ~0.2s
补满缺口或申请人全部失败后：点「清空」（zudui_qingkong）清除
  残留申请（队伍已满/对方已加入其他队伍的陈旧请求）       ~0.1s + 0.3s
关闭申请面板：悬停 0.15s + 点击 + 等面板消失最长 4s       ≤4s（每 0.5s 查一次）
允许成功 ≥1 人 → 立即 continue 重查（不 sleep）
```

## 4. 查人数子流程时序（team.check_team_min）

```
面板未开 → 先查申请人证据（2026-11-02 新增：命中即返回 wait
          确定性队长，不再开面板、不算「队长无法判定」）
开组队菜单：点按钮 + 等菜单弹出最长 1.5s（3 × 0.5s）
点「队伍信息」+ 等面板打开最长 4s（面板为服务器数据，稍慢）
双模板判定队长（解散/离开比分数）+ 人数计数 + 成员 OCR
关面板：悬停 0.15s + 点击 + 等关闭最长 4s
一次完整开合实测 5~7s
```

## 5. 人满后回到领取的路径

```
监控循环返回（ready）
→ _claim_task 返回 False「队伍已补齐，下轮重试领取」
→ run_loop 记 WARN + sleep 1s（cycle_interval）
→ 下一轮：已在领取点 → 跳过预检和寻路
→ 再次进监控循环一次（_team_checked 尚未置位）：一次面板开合 5~7s 确认人满
→ 重试领取：入口点击 → 对话框 ~1.5s → 点选项 → 任务进追踪校验 ≤5s
→ 成功
```

补 3→5 人时：一次补人周期内连续允许 2 人（max_allow=缺口 2）→ 清空残留
→ 关闭 → 立即 continue 重查确认 5/5，不卡 10s。
允许失败的情况（对方已加入其他队伍）换下一个申请人继续；全部失败或
补满后点「清空」清除残留申请列表，防止陈旧申请持续占据申请待处理态。

## 6. 检查队伍开关关闭时（allow_fill=False）

不补人：_claim_task 直接返回「已点『我再想想』」，run_loop sleep 1s 下轮重试
领取——每轮都会再弹确认窗，无限重试直到人够或人工干预。
